# Development of the tool

This file is for a developer of the tool: `src/`, `tools/`, the root config files, the guide and the documents. An agent that creates screens or applies the canvas requests reads `AGENTS.md` and the files that it names, not this file.

Read `docs/canvas-tool-plan.md` before you change the tool itself. It contains the goal, the decisions, the constraints, the design, and the next steps.


## Hard constraints

- No remote server and no cloud backend. A local backend is permitted: a Node app or a different server that runs on the local machine.
- No MCP and no cloud service at runtime. An AI agent works through files and the local backend.
- Few dependencies. Each package must be available from an internal npm registry.
- The component library must be replaceable. All that is specific to one library is in its pack, `packs/<name>/`, and nothing outside `packs/`, `screens/` and `components/` depends on the library. The sample library is a pack too, a substitute for the real work library.
- No traces of other tools. Do not name other design tools, editors, or starter kits in this repository: not in code, comments, documents, file names, branch names, or commit messages. Do not copy source code or documents from them. Write each idea as our own design. The names of the stack and of the npm packages in `package.json` are permitted. The rule applies to everything that Git tracks, because that goes to the remote repository and to each clone. Local files that Git does not track are permitted; exclude them with `.git/info/exclude`, not with `.gitignore`.
- One exception to the rule above, accepted by the user: `src/editor/ui/` is copied from an open-source project with the MIT licence. Its `LICENSE.md` must stay in that folder, because the licence requires it. Do not write the name of that project in a different place.

## Commands

Each npm script of the tool, except `lint`, `test` and `test:watch`, runs the command of the tool: `node bin/canvas.js <command>` (`bin/canvas.js`, `tools/cli.ts`). `node bin/canvas.js help` (also `--help` or `-h`) lists the commands. An unknown command, an unknown option, and an argument for a command that takes none stop it with a message and the list.

- `npm run dev`: start the dev server at http://localhost:5173/: the editor at `/`, the prototype site at `/__frame/site.html` (`/site.html` sends the browser there). `npm run dev -- --port <number>` takes that port, and fails when it is in use (no next port)
- `npm run build`: type check of all code (the editor too; for a project outside the tool, its own `tsconfig.json`), then the build of the prototype site into `dist/` of the project. `dist/index.html` is the site; each address in it is relative (`base: './'`), thus the folder works at each address of a static host, also in a sub folder. The build has no editor and no `frame.html`: they need the dev server.
- `npm run lint`: oxlint
- `npm test`: run the unit tests once (Vitest)
- `npm run test:watch`: run the unit tests on each change
- `npm run check`: check the screen files with no browser (`tools/check.ts`): an error of a file, a broken relation, a marker of the part of an option that breaks a rule, a link to no screen, an element that is not from the library, an inline `style`, a raw value (a length or a color as a text literal in an attribute, and a number that stands for pixels, such as `fontSize: 14`, where the pack names the keys of its scales), a handler or a hook, a `className`, an import of the tool or of a component (not an own component in `components/`, which is a note), and a placeholder text. It prints each finding with `file`, `line:column` and kind, and exits with 1 when there is a finding. `npm run check -- <screen>…` reports only the named screens (ids or paths); the links and the relations are still read against all screens. With no pack it cannot tell an element of the library from a different one, thus it has no finding of the kind `not-library`.
- `npm run tokens`: write `tokens.json` from the token entry of the library pack. With no pack it writes no file, says so, and exits with 0; with an error of the packs (two packs, a manifest that is not valid) it exits with 1.
- `npm run preview`: serve the built site from `dist/` at http://localhost:4173/ (`-- --port <number>` as for `dev`). The site needs a host or this command: a browser does not run its scripts from a file opened with a double click. Use `npm run dev` to work.
- `npm run status`: the state of the project (`tools/status.ts`): the library and its level, the provider, the tokens by group, the library skill, the `AGENTS.md` of the pack, the screens, the findings of the check, the command of the agent, a dev server that runs (from `.canvas/dev.json`), the version of the tool that wrote the copy of the guide in a host, and the next step of the setup: while the library skill or the `AGENTS.md` of the pack is missing, it names that step, not "the setup is done".
- `npm run init`: set up a project (`tools/init.ts`). In the tool repository (standalone) it writes the pack of level 1 (`connected`) with its `package.json`: `npm run init -- --library <package>@<range>` (with no range, `latest`), and says to run `npm install`. In a host (`npx canvas init` in the folder of an ongoing project that has the tool as a development dependency, or the script of a clone next to it) it writes `canvas/`: `canvas.config.ts`, `tsconfig.json` (with `paths` for `canvas-editor/tokens` into the tool), `.gitignore`, the pack of the library that the host has installed (with no `package.json`), an empty `tokens.json`, and a copy of `AGENTS.md` and `guide/` with a line that names the version of the tool and the line of the command there (`npx canvas <command>`, or the script of the clone); at the host root the stubs of the skills (`.agents/skills/`, and `.github/skills/` and `.claude/skills/` when their parent folder exists) and the block in `AGENTS.md` (made when it is not there), `CLAUDE.md` and `.github/copilot-instructions.md` (when they exist). With no `--library` it takes the one dependency of the host with React as a peer dependency (a peer dependency of a different candidate is left out), and with more than one it lists them and stops. `--library ./<folder>` takes a folder of the host. A file of the project is written only when it is not there; the copy of the guide, the stubs and the block are written again when they differ: a second run changes nothing. A folder that is not empty and has no `canvas.config.ts` is a refusal. It never runs `npm install`. The templates of the files are in `tools/templates/`.
- `npm run sync`: in a host, write the copy of the guide, the stubs and the block again (after an update of the tool), and remove a file of the copy or a stub that the guide no longer has; standalone, the stubs only.
- `npm run agents`: write the stub of each skill of `guide/skills/` into `.agents/skills/`, `.github/skills/` and `.claude/skills/` (`agentsPlan` in `tools/init.ts`, the same plan as in a host, where it refuses a project that is the host root or has no `canvas.config.ts`, as `sync` does), and remove a `canvas-*` stub whose skill is no longer in the guide, only when its `SKILL.md` is a stub of the tool (`isStub` in `tools/adapters.ts`) and the folder has no other file. Run it after a change of the `name` or the `description` of a skill; a test checks that the plan writes and removes nothing in this repository.
- `npm run export -- <folder>`: write the clean tool into a new or empty folder outside the project: each tracked file except `packs/**`, `screens/**`, `components/**`, `docs/plans/**` and `package-lock.json`, with the tracked empty `packs/.gitkeep` and `screens/.gitkeep`, and a new lock file when npm can reach the registry. It copies each file as it is on the disk: a change that is not committed goes into the export (the report counts these files), a file that Git does not track does not, and a tracked file that is missing on the disk stops the export before it copies anything. A relative folder is relative to the folder where you run the command. It prints what a person does next there.
- `CANVAS_NO_PACK=1` before a command (`CANVAS_NO_PACK=1 npm run dev`, `… npm run build`, `… npm run tokens`): the tool finds no pack, as in the clean tool. It checks the "no library" paths with the pack still on the disk; the type check still reads `packs/` and `screens/`.

## Stack

Node 22.12 or later (the floor of Vite 8 on Node 22). Node runs no TypeScript file of the tool directly: `bin/canvas.js` is plain JavaScript and loads `tools/cli.ts` and each script through the module runner of Vite (`runnerImport`), which strips the types, also below `node_modules`, where Node refuses to. Run a script of `tools/` by hand as `node bin/canvas.js <command>`. Vite 8, React 19, TypeScript 7, Tailwind CSS 4 (editor only). In standalone the packages of the component library are in its pack: `packs/<name>/package.json` is an npm workspace (the root `package.json` has `"workspaces": ["packs/*"]`), and `packs/<name>/AGENTS.md` names them. With no pack, the install has no library. In a host the host installs the library, and the pack has no `package.json`. The editor UI in `src/editor/ui/` uses Base UI (`@base-ui/react`), `@phosphor-icons/react`, `class-variance-authority`, `clsx` and `tailwind-merge`. The build step uses `parseSync` and `Visitor` from `vite` and `magic-string`.

The package. A host project installs the tool as a development dependency, from a file of `npm pack` or from a Git address. npm then installs only the `dependencies` of the tool, thus each package that the tool runs is there: the editor packages, React, `vite`, `@vitejs/plugin-react`, `@tailwindcss/vite`, `tailwindcss`, `magic-string` and `typescript`. `devDependencies` has only what the tests, the lint and the type check of the tool need. `files` names what npm packs: `bin/`, `src/`, `tools/`, `guide/`, `public/`, the three HTML entries, the config files that the command gives Vite, the `tsconfig` files and `AGENTS.md`, with no test file. `exports` has `./tokens` (`src/tokens/index.ts`, for the token entry of a pack) and `./package.json`. The tool has no install script (`prepare` and the others): npm 11 asks for an approval of each one, and a version of npm that runs `prepare` for a Git dependency first does a full install of the tool. `tools/package.test.ts` checks these rules: each relative import of a packed module is packed, each package that the tool runs is a regular dependency, and no install script.

Testing: unit tests use Vitest in the `node` environment, in `*.test.ts` files next to the code (`src/`, `tools/`, `packs/`). Keep logic in pure functions with tests; components read the DOM and call them. Tests use plain objects in place of DOM nodes and React records, not a DOM library. Check interface changes in the browser pane: `.claude/launch.json` starts the dev server with the pack (`canvas-editor`, port 5173) and with `CANVAS_NO_PACK=1` (`canvas-editor-no-pack`, port 5174) for the "no library" state, and `npm run preview` (`canvas-site`, port 4173) for the built site; run `npm run build` before it.

## Layout

**The tool and the project are two folders.** The tool is the code: `bin/`, `src/`, `tools/`, `guide/`, `AGENTS.md`, the HTML entries and the root config files. The project is the content: `canvas.config.ts` (in a project outside the tool, with `widths` and `agent` only), `screens/`, `components/`, `packs/<name>/`, `tokens.json`, `.canvas/`, `dist/`, and in a host a copy of `AGENTS.md` and `guide/`. Two modes run the same code:

- **Standalone:** this repository is the tool and the project at once (the project root is the root of the tool). The sample pack and screens are here.
- **In a host:** the project is `canvas/` of an ongoing project, the host, which `canvas init` writes. The tool is a development dependency of the host (below `node_modules/canvas-editor`, run as `npx canvas`), or a clone next to the host (run as `node <clone>/bin/canvas.js`). The root of Vite stays the folder of the tool; each plugin and script takes the project root from `tools/project.ts`, and the agent works in the host root.

`canvas dev` is **two Vite servers on one origin** (`tools/dev.ts`, `tools/react-resolve.ts`): the editor server on the port, with the React of the tool, and the frame server below `/__frame/`, with the React of the project, for the frames and the site. A frame must have one copy of React, the one of the project, and the editor one copy, the one of the tool; one server cannot give the two.

Three HTML entries keep the editor, the screens and the site apart:

- `index.html` is the editor. It loads `src/editor/main.tsx` and `src/editor/editor.css` (Tailwind and the editor theme). It never imports a screen or the library. Dev server only.
- `frame.html` is one screen. It loads `src/frame/main.tsx`, which renders the screen of `?screen=<id>` in the wrapper of the library (`LibraryProvider` from `virtual:canvas-library`). The frame server serves it at `/__frame/frame.html` (see "Two servers" below). It has no Tailwind and no editor styles. Dev server only.
- `site.html` is the prototype site. It loads `src/site/main.tsx`: with no hash (or `#/`) the index of the screens by flow, with `#/<screen id>` that screen as a full page in the wrapper of the library, at the width of the window, and for an id that no screen has a message with a link to the index. It has its own small stylesheet (`src/site/site.css`): no Tailwind, no editor theme, no library. It is the one entry of the build, which writes it as `dist/index.html` (`tools/site-plugin.ts`); in the dev server the frame server serves it at `/__frame/site.html`, and `/site.html` sends the browser there.

Folders:

- `canvas.config.ts`: plain data. The screen widths, the screens folder, the token file, the work folder (`.canvas/`, ignored by Git). `screens` and `components` are also literals in `tsconfig.app.json` and `.oxlintrc.json` (`components` also in the template of the `tsconfig.json` of a host, and as `componentsFolder` in `tools/check.ts`), and `tokens` in the guide and the messages of the editor; change them together. The frame, the site and the editor read the screens and the token file of the project through virtual modules (`tools/screen-modules.ts`), not through a glob below the root of Vite. `work` is also a literal in `guide/requests.md`, in the skill `canvas-apply`, in the older fixed sentence for the agent (`olderAgentSentence` in `src/editor/requests/agent-sentence.ts`; `tools/guide.test.ts` and its own test check them), and in `.gitignore`; change them with it. The fixed sentence names only the guide: `agentSentence(guidePath)`, `Apply the canvas requests as AGENTS.md says.`; for a project in a host the dev server gives the editor the path relative to the host (`project.guide` of `virtual:canvas-screens`, `canvas/AGENTS.md`). `agent` is the way of "Send to the agent" (`AgentSetting`): `'auto'`, `'clipboard'`, the name of a preset (`'vscode'`), `{ command, args }`, or `null` (an older form of the clipboard); here `{ command: 'code', args: ['chat', '--mode', 'agent', '--reuse-window'] }`, the preset `vscode` written out. Keep that tracked line as it is: a user who wrote a full path there would get a conflict at a pull. A project in a different folder can have its own `canvas.config.ts` with `widths` and `agent` only (`tools/project-config.ts`); with no `agent` it gets `'auto'` (`projectDefaults`), and the template of `canvas init` writes `'auto'`. The dev server gives the editor its widths (`project.widths`), and the command of `agent` starts in the host root.
- `packs/<name>/`: the library pack, all that is specific to one component library. The tool finds the pack by itself (`tools/pack.ts` reads `packs/*/pack.json`); no config names it. The folder name `packs` is `packsFolder` in `tools/pack.ts` and a literal in `package.json` (`workspaces`), `tsconfig.app.json` (`include`) and `vitest.config.ts` (`include`); change them together. `vite.config.ts` reads the pack once, when the dev server or the build starts, and gives it to the plugins. The dev server restarts by itself when a pack folder, a `pack.json` or the provider `library/provider.tsx` in `packs/` is added, changed or removed and the pack is then different (`tools/pack-plugin.ts`), and the open editor reloads; a new pack restarts it only when its provider exists, and a change of other files of the pack needs no restart. The tool has two states:
  - **no pack**: the tool builds and the dev server starts; the canvas and each frame say "No library is connected" with the sentence for the agent, `Connect a library as the skill canvas-library-setup says.` (`connectSentence` in `src/frame/library-setup.ts`; README.md writes it too, and a test checks the two files against it: change them together); `npm run tokens` writes no file; no element has the origin `library`. With no pack, an agent does not create a screen: it follows `canvas-library-setup`.
  - **one pack**: that is the library. Its level (`levelOf` in `tools/pack.ts`) is `connected` when the token file of the project has no token (the token entry gives an empty list): the screens render, the canvas shows "The tokens are not set up" with the second sentence, `Set up the tokens of the library as the skill canvas-library-setup says.` (`tokensSentence`, `NoTokens` in `src/editor/canvas/NoLibrary.tsx`; AGENTS.md writes it, and a test checks it), the Design tab has a note in place of the count of the values with no token, and no value is a `no-token` issue, because no group has a token; the check is the same. With tokens, or with no token file or one that is not valid (the editor then shows the error of the file), the level is `ready`.

  More than one pack, or a manifest that is not valid, stops the dev server at its start, the build and the token script with a message that names the cause. When the error comes while the dev server runs, the server shows the message in its output and keeps the pack that it has until the files are fixed. A choice between packs is not built: to try a second library, move the first pack out of `packs/`. A pack has:
  - `pack.json`: `{ "name": "<name>", "sources": [ "<npm package>", "./<folder of the host>" ], "scaleKeys": [ … ] }`. `sources` are the npm packages of the components, and the folders of code of the host (a path that starts with `./`, `../` (also `.\` and `..\`), `/` or a drive of Windows, relative to the host root; `isFolderSource`, `isAbsoluteSource`); the older `"package"` is a list of one, and goes first when the two are there. `librarySources` gives the packages and the folders relative to the project root (a folder on a different drive of Windows stays absolute), which `originOf` in `tools/jsx.ts` reads: a package or a path below it, or a relative import into a folder, has the origin `library` (a folder above the project, `..`, takes no path above that folder); an alias of the bundler of the host is not read. `sourceFolders` gives each folder source as an absolute folder: the token plugin watches it, and the dev server serves it. The check (`check.ts`) gives no `import` finding for an import of the library, also from a folder with JSX. `scaleKeys` is optional: the keys of the style object of the library, and the props of the same name, whose number is a step of a scale of the theme (`padding`, `gap`, `borderRadius`). A number under a different key of a size (`sizeKeys` in `tools/screen-facts.ts`) is a count of pixels: the check finds it, and the editor marks its element. A number in a call (`theme.spacing(2)`) is not read. With no list the check finds no number. A new list restarts the dev server. `name` is the folder name (lowercase letters, numbers and hyphens) and the `<name>` of its library skill `canvas-library-<name>`. 
  - `package.json` (optional; a pack in a host has none, the host installs the library): an npm workspace with the packages of the library, `"private": true` and `"type": "module"`. npm installs them into the root `node_modules`.
  - `AGENTS.md`: the instructions that are specific to the library: its packages, its breakpoints, how an edit is written with it, and the link to its library skill.
  - `library/`: `provider.tsx` (the wrapper of a screen, `LibraryProvider`), `tokens.ts` (`export function tokens(): Token[]`, the token entry), the theme if the library has one, and their tests.
  - `skills/`: the library skill `canvas-library-<name>/`, and the guidance of the library, copied as `canvas-library-setup` says.

  The core (`src/`, `tools/` and `bin/` with their tests, the root config files and the three HTML entries) imports no path in `packs/` and no package that the root `package.json` does not declare: the packages of a pack, and the packages that npm installs with them, are not a part of the core. It reads the pack only through `virtual:canvas-library` and the token entry, which the token script loads by a computed path. `tools/core-clean.test.ts` checks this; write no such import.
- `screens/<flow>/<name>.tsx`: the screens, one file for each. `guide/screen-files.md` has their rules. `screens/<flow>/flow.json` (`{ "order": [ … ] }`) gives the sequence of the base screens of a row; the screen actions write it. The screens are content, neither a part of the tool nor of the pack; the export leaves them out.
- `components/<Name>.tsx`: the own components of the project (`components` of the config, `componentsFolder` in `tools/check.ts`): the parts that the library does not have and that the user asked for, or the components of the application that the user asked to bring with a screen (`guide/screen-files.md`; "Bring a screen that exists" in the skill `canvas-screen`). A screen imports them by a relative path. They are content, as the screens: the export leaves them out. The element-to-code step gives their JSX the location prop too (`source-location-plugin.ts`), thus the editor selects and edits an element inside one as on a screen, with `file` of its target in `components/`, and the markers and the Issues list show the component and each plain element in it as not from the library. The check gives a screen no finding for such a component, one note that names them (`isOwnComponent`; an import that leaves the project is not one), and one note for each component file with the counts of what is in it (plain elements, `style` attributes, raw values, handlers, links; `ownComponentNotes`). An own component is a `.tsx` file: only that form gets the location props. A change of a component file reloads the frames of the screens that import it (`screensUpdate`), as a shared file of the screens folder does, thus the editor reads the new places from a new document. An element inside an own component has no 'Ask for options' (`barActions`, `inOwnComponent`): an option is a copy of the screen file.
- `AGENTS.md` and `guide/`: the guide for the agent that creates screens and applies the canvas requests. `AGENTS.md` is short: the purpose, the map of the folders, the table of the situations with the file to read in each, the fixed things, and the commands. `guide/screen-files.md` and `guide/requests.md` are the references (the second has the marker of the block of an option, `canvas-part`, in "Options"; the text of the marker is `partMarker` in `tools/part.ts`, and `tools/guide.test.ts` checks that the guide writes it), and `guide/skills/` has the six skills of the tool. Each path in a Markdown link is relative to its file, thus the same text is right where a copy of the guide lies. The guide writes a command as `canvas <command>`; one line of `AGENTS.md` says how it runs here (`npm run <command>`). It names no lint step. `tools/guide.test.ts` checks the links, the table and the length of `AGENTS.md`; `tools/skills.test.ts` checks the head of each skill. The table of `AGENTS.md` keeps a row for each name that an older pack points to ("Screen files", "Requests", "How to create a screen"). This file is for a developer of the tool, and `CLAUDE.md` loads it together with `AGENTS.md`.
- `.agents/skills/`, `.github/skills/`, `.claude/skills/`: the stubs of the skills, written by `npm run agents` (see "Skills"). Do not change them by hand.
- `bin/canvas.js`: the command of the tool, `canvas <command>` (the `bin` of `package.json`). Plain JavaScript: it imports `vite` by its bare name, thus from the folder of the tool (npm can put the packages of the tool below its own `node_modules`), loads `tools/cli.ts` through `runnerImport` of Vite, and calls `main` with the arguments. An error of a command shows as its message; `CANVAS_DEBUG=1` shows the stack too.
- `tools/`: the Node side: the command, the Vite plugins and three scripts, `build-tokens.ts` (`npm run tokens`), `check-screens.ts` (`npm run check`) and `export-tool.ts` (`npm run export`). Each plugin and script has its pure logic in a tested module next to it. Each plugin and script reads the content from the project root (`project.ts`), not from the root of Vite: `vite.config.ts` gives the project to each plugin, `server.fs.allow` has the tool, the project, the host and each folder source of the pack, also one outside the host (not a host or a folder that is the home folder, a folder above it or the root, `hostProblem`), and the file watcher leaves out the caches `.canvas/vite*` of the project. A frame and the site import the screens of the project through `virtual:canvas-screen-modules`, and the editor reads `tokens.json` of the project through `virtual:canvas-tokens` (`screen-modules.ts`). The caches of the dependency step are `.canvas/vite-editor` and `.canvas/vite-frame` of the project.
  - `cli.ts`: `commandOf` (pure) reads the arguments: the command (`dev`, `build`, `preview`, `check`, `tokens`, `status`, `init`, `sync`, `agents`, `export`), `--project <folder>` (for each command but `export`, which works on the tool), `--port <number>` (for `dev` and `preview`), `--library <library>` (for `init`), and the other arguments, also each one after `--`; only `check` and `export` take arguments. `dispatchOf` (pure) finds the project (`projectRoot` of `project.ts`; for `init` `initProject`: the option, the variable, the tool when the command runs in the tool repository, else `canvas/` of the host that each later command finds for it, `hostRoot` of `<current folder>/canvas`: in a package of a repository with workspaces, the root of the repository; the folder may not exist yet), refuses a folder of the option or of the variable that is not a folder, a lookup that found no project (`noProjectProblem`; not for `export`, which works on the tool), and for `init`, `sync` and `agents` a host that is the home folder, a folder above it, or the root (`hostProblem`). `main` sets `CANVAS_PROJECT` to the folder that it found, in the case of the letters that the disk has (`diskCase` of `project.ts`: the file watcher gives each path so, and the plugins compare paths as they are; a folder that is not there yet gets the case of its nearest parent that is there; the current folder and `toolRoot` are in that case too, thus each relative path between the project, the host and the tool is right), thus the Vite config, each script and each child process read the same project, and runs the command: `dev`, `build` and `preview` through the JavaScript API of Vite; `status`, `init`, `sync` and `agents` as functions of `status.ts` and `init.ts`; `check`, `tokens` and `export` as their script, loaded through `runnerImport` with its arguments in `process.argv` (`scriptOf`).
  - `project.ts`: the project root and the host root. The project is the folder of the content (`screens/`, `packs/`, `tokens.json`, `.canvas/`, its own `canvas.config.ts` and `AGENTS.md`); the root of Vite stays the folder of the tool. `projectRoot` (pure): `--project`, then `CANVAS_PROJECT`, then the nearest folder from the current one upward that has `canvas.config.ts` (that folder) or `canvas/canvas.config.ts` (its `canvas` folder), then the tool (`toolRoot`). `hostRoot` (pure): the folder where the agent works; a project with its own `.git` or `package.json` is its own host, else the nearest folder above it with `.git` and a `package.json` (the root of a repository with workspaces, also from a package below it), else the nearest folder above it with one of the two, else the project. `noProjectProblem`: a lookup that ended at the tool found no project when the tool is installed, or when the command of a clone runs outside the folder of the clone. `guidePathOf`: the path of the guide of the project relative to the host (`AGENTS.md`, `canvas/AGENTS.md`), which the fixed sentence names. `cacheMatcher`: the caches of the dependency step in the work folder (`.canvas/vite*`), which the file watcher leaves out. `currentProject` calls `projectRoot` with the values of the process, in the case of the disk (`diskCase`), as the command does; `vite.config.ts`, `build-tokens.ts` and `check-screens.ts` use it. `toolRoot` (with `/`, no `/` at the end, in the case of the disk) is the one folder of the tool for each module. `folderProblem`: a folder of the option or of the variable that is not a folder. `parentOf`: the parent of an absolute folder, null at `/` and at the root of a drive of Windows (`C:/`), thus each lookup upward ends there; ## Conventions

- Editor styling uses Tailwind 4 classes and the editor theme in `src/editor/ui/theme.css`. The theme is set with `data-editor-theme` (`light` or `dark`) and the class `dark` on the root element. A line between two parts of a panel is `border-[color:var(--editor-line)]` (`src/editor/editor.css`), never `var(--border)` as it is: `--border` of the theme is the text color at full strength, and the copied components mix it down.
- Write new files with single quotes and no semicolons, as in `src/`.
- Relative imports in `tools/`, `packs/<name>/library/`, `src/tokens/`, `src/related/`, `src/requests/`, `src/frame/library-setup.ts`, `src/frame/screen-id.ts`, `src/frame/screen-link.ts`, `src/site/entry.ts`, `src/words.ts`, `src/editor/requests/agent-sentence.ts` and `canvas.config.ts` carry the file extension (`.ts`, `.tsx`), because these files are also loaded with no bundler (the module runner of Vite, the config loader).
- Editor code that reads a frame gets `getComputedStyle`, `ResizeObserver`, `MutationObserver` and `matchMedia` from the window of the frame document (`frameWindowOf` in `src/editor/frame-window.ts`), and never uses `instanceof` with the classes of the editor window (see `src/editor/tokens/read-styles.ts`, `src/editor/tokens/declarations.ts`, `src/editor/selection/pick.ts`).
- A node that the editor keeps (the selection, a target) can outlive its frame: after a reload of the frame it stays connected to its old document, which has no window. `isConnected` is then true, and a read of its styles fails. Check `inLiveFrame` (`src/editor/frame-window.ts`) before you read a kept node.
- A script of a command (`npm run tokens`, `npm run export`) does its work when it loads, thus a test cannot import it. Keep such a script thin, and put its decisions in a pure module with tests: `build-tokens.ts` with `token-state.ts`, `export-tool.ts` with `export.ts`, `check-screens.ts` with `check.ts`.
- The type check of `tools/` and `bin/` (`tsconfig.node.json`, with `checkJs` for the JavaScript of `bin/`) has no DOM library. A test in `tools/` that imports editor code with DOM types needs `/// <reference lib="dom" />` (see `tools/source-location.test.ts`).
- `src/editor/ui/` is copied code with a different style (double quotes, semicolons). Do not reformat it. Lint ignores it. Change it only when the editor needs the change.
- The editor and the screens have separate styles. Only `src/editor/editor.css` imports Tailwind and the editor theme, and it makes classes from `src/editor/` only. A screen gets only the styles of the library. Do not import editor styles into a frame or a screen.
- The editor writes into a frame document only through the preview (`src/editor/preview/apply.ts`): the style element `style[data-canvas-preview]` in the head and the attribute `data-canvas-edit` on the nodes of each target, plus the inline `order` of the children of a parent with a sequence edit and the text of an element with a text edit. Each of these goes out when its edit goes out. Write nothing else into a frame: the inspector and the Issues list read the frame, and other writes change what they read. The Preview switch writes nothing into a frame either: it reads the link under the point. The drag of a move writes nothing into a frame either: its listeners and its cursor are on the overlay of the frame (`[data-frame-overlay]`), in the editor document.
- The frame decides the sequence that a move shows: read the shown sequence and the rectangles of the siblings from the frame document at the same moment (`rectsNow`, `shownOrder`: the computed `order`, then the index), not from the edits. The preview can skip an edit, a different sibling can have the open move, and the library can set `order` itself.
- The pins, the bar of the selection, the bubble, the options panel, the dots of the edits, the line of the drop of a move, the arrows of the links and the names of the flows are in the overlay of the canvas, in the editor document, never in a frame: they read the rectangles of the frame nodes and write nothing there. Their size is fixed on the screen at each zoom. A part that takes the pointer (a pin, the bar, the bubble, the options panel) has `pointer-events-auto` and is above the overlay of each frame, thus a click on it is not a pick; a dot, the line of the drop, an arrow of a link and the name of a flow have no pointer. A part that scrolls inside the canvas (the list of the bubble, a text area of a comment box or of the options box, the box of the error of a screen file) has `data-canvas-scroll`: the wheel listener of `Canvas.tsx` then leaves a wheel event alone that it can scroll (`canScroll`). A floating panel is placed by a pure function (`panelPlace`, `barPlace`) through `useFloatingPlace`, stays out of the strips of the notice and the toolbar (`overlayStrips`), and uses no popover that renders outside the canvas.
- A component that reads the edits of one screen for the canvas (the pins, the dots, the pins and the mark "Options asked" of the title row, "Keep this option") is a small child of its own for each frame, with `useScreenEdits`, as `IssueCount` in `Frame.tsx` is for the issues. `App.tsx` and `Frame` do not read the edits store, and `App.tsx` does not subscribe to the selection (a zoom reads `selection.get()` at the click): a render of `App` renders each frame. Read the rectangles of the targets through `useScreenRects`: one measure for each screen (`useMeasureRects`), which reads a frame document only after a change, not at each new view. Do not add a second measure of the same targets.
- The box of a frame in the layout (`FrameBox`) is the box of its iframe, also for a frame with a crop (an option with a part): place a rectangle of the frame document from the corner of the box (`canvasRectOf(view, box, nodeRect)`), as before. Code that needs the rectangle that the user sees (the title row, a fit of the view, the place of a thing next to the frame) reads `shownRect(box)`, not `box.width` and `box.height`. A new mark of the canvas that reads a frame keeps to the crop with `inCrop`. The crop is only in the editor document (`clip-path` on the box of the iframe): write nothing into the frame for it.
- The listeners of the keys of the window (`useWindowKeys` in `src/editor/hooks.ts`) do nothing in a window that is narrower than the editor (`narrowQuery`): the message covers the editor there. One key listener in `App.tsx` handles Escape and the keys of the view; a second one, `useHistoryKeys`, handles undo and redo (Ctrl or Cmd with Z, with Shift for redo; `historyKey` in `src/editor/focus.ts`), and does nothing while a text field has the focus. Escape does what `escapeAction` (`src/editor/focus.ts`) says, in this order: it cancels a drag of the selected element (`moveDrag.dragging()`, read at the key), then closes the floating panel (the bubble or the options panel), then turns Preview off, then clears the selection. A field that uses Escape for its own work (it puts back its text) prevents the default, and the listener then does nothing. An Escape that ends the composition of a text (`isComposing`), and one while a dialog of the screen actions is open, do nothing there either. Do not add a second Escape listener. The keys of the view are matched by `event.code` (`viewKey`: `Shift+1`, `Shift+2`, `Shift+0`; `C` is a key of the bar, `barKey`), with no Ctrl, Cmd or Alt, and not while a text field has the focus. The keys of the selection (Delete, Backspace, `C`, and the arrow keys; `barKey`) are a second listener, in `SelectionBar.tsx`, mounted while an element is selected; it does nothing while a text field, the bubble, the options panel, a pin, the menu or a dialog of the screen actions, or an open list of a select or a menu (a portal) has the focus (an open dialog of the screen actions, the bubble and the options panel count also with the focus on the body), while a dialog of the screen actions is open (also with the focus on the body), for a held key, while a drag runs, or when the default is prevented. An arrow key moves the element only when the focus is on the canvas (`[data-canvas]`, the root of `Canvas.tsx`) or on the body (`arrowsFree`, `focusOnCanvas`): a positive rule, thus a control of the panel, and a list that it opens outside the panel, keeps its arrows. The listener prevents the default only when the move ran, thus an arrow of the other axis or at the end of the sequence is left alone.
- Import the values of `virtual:canvas-screens` (the list, `library`) only in a module that exports React components and nothing else (for example `App.tsx`, `Inspector.tsx`, `Changes.tsx`, `SelectionBar.tsx`, `Site.tsx`, `Index.tsx`). The dev server updates the list after each change of the screens folder, and such a module is refreshed in place. `ScreenPage.tsx` imports the list for its side effect only: the update then refreshes it too, and its import of `virtual:canvas-screen-modules` gets the new map. A refresh runs each effect of the components of the refreshed module again, with no regard to their dependencies: an effect that owns work that must live on (the request sync and the issues sync) is in a child component of a module that does not import the list (`RequestSync.tsx`, rendered by `App.tsx` with the list as a prop), not in a hook of such a module. An entry that calls `createRoot` (`src/editor/main.tsx`, `src/site/main.tsx`) is not refreshed: if it imports the list, each new screen reloads each page, the editor too. A module of plain functions takes the list or the ids as an argument (`collect.ts`, `operate.ts`, `route.ts`); a type import is permitted.
- An edit can have no target: a comment or an `options` item on the screen has `target: null`, and a `keep` item always has it. New code that reads `edit.target` takes `null`, or reads only placed edits (`isPlaced`, `PlacedEdit`). The preview reads the list only through `liveItems`, thus it never sees a comment, an `options` item or a `keep` item; keep it so.
- Code that matches the tokens to the values of a frame takes them through `frameTokens(tokens, document)` (`src/editor/tokens/frame-tokens.ts`), not the list of `tokens.json` as it is: a token with `media` values has a different value in a narrow frame, and the list as it is would show "no token" there.
- The site and the index have no Tailwind and no editor styles: `src/site/site.css` has plain class rules, thus the index looks the same with each library and with no library. A screen page gets only the styles of the library. Only `ScreenPage.tsx` imports the library, and `Site.tsx` loads it lazily: do not import it, or a module that imports it, into a different module of the site, or the styles of the library go into the index.

## Skills

The first two are the design skills: they name no component and hold for each library. The others are the library layer: the library skill and the copied guidance of a library are in its pack, and a different library brings a different pack, as `canvas-library-setup` says.

The skills of the tool are in `guide/skills/`, one folder for each skill, next to the two references of the guide, `guide/screen-files.md` and `guide/requests.md`. `AGENTS.md` names each skill with its path and says when to read it, thus an agent that loads no skill by its description finds them too. For an agent that loads a skill by its description, `npm run agents` (`canvas agents`) writes a stub of each skill into `.agents/skills/`, `.github/skills/` and `.claude/skills/`, the folders that agents scan: the `name` and the `description` of the skill, and one line that sends the agent to the skill in `guide/skills/`. A stub has no content of its own; after a change of the head of a skill, run `npm run agents`. The prompt files of one agent are gone (2026-11-23): they were not found at work, and their format is for one agent. The skills of a library are in `packs/<name>/skills/`, in the same form; an agent reads them through the link in `packs/<name>/AGENTS.md`, not by their description. The name in `SKILL.md` must be the same as the folder name, with only lowercase letters, numbers and hyphens; the description is 1024 characters or less.

A skill is a short `SKILL.md` and, for a skill with many topics, a folder `references/` with one file for each topic. `SKILL.md` has the rules that apply each time and a table that links to each reference file with a relative Markdown link (`./references/<name>.md`) and says when to read it. An agent loads a reference file only through such a link, thus a file with no link is never read. In `canvas-screen-design` each row of the table also names the sections of the file to read, after the colon, by their headings: when you rename a `##` heading in a reference file, change its name in the table too. A new topic is one new section or one new reference file, and one row in the table. `AGENTS.md` lists the skills, not their reference files.

- `canvas-screen-design`: a core skill. It names no component and no token, thus it holds for each design system. Read it each time you create or change a screen in `screens/`. It says what to put on a screen and what to leave out: the task and the scenario before the code, the rules that hold for each screen, one reference file for each part of a screen (flows, forms, lists, tables, navigation, actions, controls, icons, motion, sound, messages, labels, text pages, layout), a check of each finished screen for access, and the rules for work with a design system, and what to tell the user after the work. New guidance goes into the file of its part; a new file is only for a part with no file. Do not write the name of a component, a prop or a token of one library into this skill: that belongs to the library skill.

- `canvas-information-display`: a core skill for data on a screen. It names no component and no chart library. Read it, together with `canvas-screen-design`, each time a screen has a chart, a diagram, a map, key numbers, numbers that the person compares or follows in time, results of a survey or a report, or a comparison of two or more things. It says what form the data get, what a picture of data must not do, and how to build a chart from the plain parts of the library with each size computed from the data. The agent gives one reply for the two skills.

A library needs no chart package: the agent builds bars from the plain layout parts of the library, and a line or a scatter as one `svg` element with colors from the palette; `packs/<name>/AGENTS.md` names the parts. A size that is computed from a value shows in the Issues list as a value with no token; that is expected for a chart, and the agent names it in its reply.

A screen is now a picture of one state: it has no state and no handlers, and each state is its own screen file, with `stateOf` set to the id of its screen (`guide/screen-files.md`). The report names the states that the screen has in use and that are not drawn. Its one behavior is a link to a different screen (see `guide/screen-files.md`): the control that leads to the next state links to the screen file of that state, and a control whose target is not drawn has no link and is named in the reply. The skill gives the rules of behavior (undo, waits, motion, hover) for a screen that operates too, because screens can become interactive later; until then the agent draws the states and names the behavior in its reply.

- `canvas-library-<name>`: the library skill, in the pack. It has the tokens in code, the component for each decision of the design skills, the defaults of the library to keep, the rules of the library that win over its override, and what the library lacks. Add a row to it when you meet a case that it does not cover.

- `canvas-library-setup`: how to connect a library as a pack, in two levels. It starts with `canvas status`. Level 1 is `canvas init` (the pack with a plain provider and an empty token entry); level 2 is the provider from the entry of the host application, the token entry with a helper, `scaleKeys`, the guidance that the library already has, the library skill and the `AGENTS.md` of the pack. The proof is `canvas status`, a sample screen with no finding of `canvas check`, and `canvas build`; the checks on a page are the last, optional part. It asks nothing that it can find or decide. The details are in its references (`pack-files.md`, `tokens.md`, `existing-guidance.md`, `contract.md`). With no library connected, an agent runs level 1 before a screen; at level 1 it can create a screen (`canvas-screen`, "Before the tokens are set up").

The three entry skills (`canvas-screen`, `canvas-apply`, `canvas-check`) are short: each has the sequence of one job and sends the agent to `guide/screen-files.md` and `guide/requests.md`, which stay the full guide. They exist because the agent at work loads skills, and did not load prompt files (the test at work of 2026-11-23). A test checks that each skill has the name of its folder, and that `canvas-apply` has the fixed sentence and its older form in its description.
