# Screen files

The rules of a screen file. A path in this file is relative to the folder of the project (the folder of `AGENTS.md`), except a Markdown link, which is relative to this file. `canvas <command>` runs as `AGENTS.md` says.

- **One screen is one file,** `screens/<flow>/<name>.tsx`, with a default export (the screen) and `meta`. The screen id is the path with no extension (`onboarding/welcome`). One folder is one flow, and one row on the canvas. Each `.tsx` file in the folder is a screen, also in a sub folder.
- **The sequence of a row.** `screens/<flow>/flow.json` can give the sequence of the base screens of a flow on the canvas and on the site: `{ "order": ["welcome", "workspace"] }`, the file names with no extension. The named screens come first, in that sequence; each other base screen comes after them, by name. With no file, the row is by name. States and options are not in the list: they stay with their base. A new screen needs no entry. A file that is not valid counts as no file: the canvas shows a mark with the error at the name of the row, and `canvas check` reports it (kind `file`). "Move left" and "Move right" in the menu of a frame write this file.
- **The tool moves, renames and deletes screens.** The menu at the end of the title row of a frame has "Rename…", "Change the title…", "Move to flow…", "Move left", "Move right" and "Delete…". The tool does each at once, and only what the action fully gives: it moves whole files, writes `flow.json`, and replaces the text literals that name a screen (the address of a link, `stateOf`, `optionOf`) and the `title` of `meta`. It never writes markup. A rename and a move to a flow take the states and the options of the screen with it (a name that starts with the name of the screen and `-` follows the new name), change each literal link to them in the other screen files, and move their request and issues files with the ids inside them changed. A delete moves the files of the screen, its states and its options, with their request and issues files, into `.canvas/trash/<time>-<id with dashes>/`, with a `manifest.json` that lists them; "Restore" in the Project tab of the editor puts them back. Thus a file that you read before can be at a new path or gone: read the list of screens again before you write, and never write a file of the trash back into `screens/`. A link that the code computes is not changed: after a rename or a delete it is a `broken-link` issue, as each link to a deleted screen is.
- **`meta`** is read with a parser, not imported: write it as `export const meta = { … }`, an object literal (it may end in `as const` or `satisfies`), with a text literal `title` that is not empty and a number literal `width` from `widths` in `canvas.config.ts` (1440, 1024 or 390). A file that breaks this shows as an error frame.
- **Only the library.** Each element is a part of the library, styled only with the library: a prop, or the override of the library with a theme value, gives a linked token. No Tailwind, no inline `style`, no raw value (`'13px'`, `'#667085'`), no plain element (`div`), unless step 6 of "How to create a screen" in the skill [canvas-screen](./skills/canvas-screen/SKILL.md) permits it (an explicit instruction of the user, the one `svg` of a chart). `packs/<name>/AGENTS.md` and the library skill give the parts and the tokens.
- **No component of your own.** A component that a screen file imports or defines is not from the library, and its parts cannot take an edit. A shared part with JSX thus goes outside the folder, and a screen does not use one. Shared sample data with no JSX can be a `.ts` file in the folder of the flow.
- **A screen is a picture of one state:** no state, no handlers, and no import from the tool. The states of one screen are full files, each with its whole markup. This repetition is intended.
- **A link is the one behavior.** A part of the library that takes an address gets `href="#/<screen id>"`, for example `<Button href="#/onboarding/workspace">`, and the id must be in the list of screens. The editor and the site follow only an `a` element with that address; section 4 of the library skill names the parts of the library that render one. With the Preview switch on, a click on a link in a frame moves the canvas to the frame of that screen; on the site, the browser opens that screen. A link with an id that no screen has is an issue of the kind `broken-link`. In rows that repeat (a list of people, each with the same button), link the controls of the one row whose target you drew, and name the others in your report.
- **The same frame around each screen of a flow.** When the screens of a flow have a header of the product or a navigation, each screen of the flow has the same one, written out in each file.
- **Related screens.** `meta` can have one more field, `stateOf` or `optionOf`, a text literal with the id of a different screen of the same flow, its base. `stateOf` marks a state of a screen (the error, the wait, the result, the empty list); `optionOf` marks an option that the user asked for (see "Options" in [Requests](./requests.md)). A screen with neither is a base screen. A field that is not a text literal, an empty text, or a file with the two fields is an error of the file. The base of a state is a base screen; the base of an option is a base screen or a state. A state has no states, and an option has no states and no options. A relation that breaks these rules (an id that no screen has, a base in a different flow, the screen itself, a chain) is not an error of the file: the screen stays visible as a base screen, its title shows the cause, and its Issues list has an issue of the kind `relation`. A screen at a different width is neither a state nor an option: it is a base screen, a full file of its own in the same flow, with the name and the title of its screen and the device of the width (`welcome-mobile.tsx`, `Welcome, mobile` for 390; `-tablet` for 1024). It links to the screens of its own width when they are drawn.
- **The name and the title of a related screen.** A state has a file name and a title that name its base and the state: `workspace-email-error.tsx`, `Workspace, email error`. An option is `<name of its base>-option-<n>.tsx` in the folder of its base; `<n>` continues after the highest number that the options of that base have (after `-option-1` and `-option-3` comes `-option-4`). Its title names its base, its number and what is different: `Welcome, option 2: fields in two columns`. The names are a convention for the agent, not a rule of the parser: the link is the field in `meta`.
- **The block of an option.** An option that the user asked for one element is still a full screen file, and it marks the block that it changed with a comment that has exactly the text `canvas-part`, on the line directly before the JSX element of the block: `{/* canvas-part */}` among the children of an element, `/* canvas-part */` before the root element. The canvas shows such an option as that block only, cropped to its size, with a switch to the whole screen; the site shows the whole screen. One option has at most one marker; an option of the whole screen and each screen that is not an option have none. When you change the file, the marker stays directly before its block. "Options" in [Requests](./requests.md) has the rules.
- **The check.** `canvas check -- <screen>…` reads the files and finds what breaks these rules in the code: a plain element, a `style`, a `className`, a raw value, a number of pixels, a handler, a hook, an import of the tool or of a component, a placeholder text, a wrong `meta`, a `flow.json` that is not valid, a broken relation, a marker `canvas-part` that breaks a rule (kind `part`), a link to no screen. It does not see the page: a content that is wider than the screen, and a value that the code computes, are only in the Issues list of the editor (`.canvas/issues/`, see "Files" in [Requests](./requests.md)).
