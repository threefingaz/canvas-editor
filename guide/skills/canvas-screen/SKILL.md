# Create a screen

A screen is a code file in `screens/<flow>/<name>.tsx`, built from the parts of the library (a screen that the user brought as it is, and an own component that the user asked for, are the two exceptions; the canvas marks what is not from the library). The user sees it as a frame on the canvas. A path in this skill is relative to the folder of the project (the folder of `AGENTS.md`); a Markdown link is relative to this file. `canvas <command>` runs as `AGENTS.md` says.

## How to create a screen

Work in this sequence. The design skills come two times: first to decide what the screen needs, and at the end to check the result. The library comes between them, because a component can only carry a decision that is already made.

| Step | Source | The question |
|---|---|---|
| 1 | the request of the user, and what the project knows about its product ("What the project knows" below) | What is the task of the person who will use the screen? |
| 2 | [canvas-screen-design](../canvas-screen-design/SKILL.md), sections 1 to 3 and the sections that its table gives; [canvas-information-display](../canvas-information-display/SKILL.md) when the screen shows data | What is on the screen, and what is not: the screens of the flow, the fields, the messages, the form of the data? |
| 3 | `packs/<name>/AGENTS.md` and the library skill that it links (`packs/<name>/skills/canvas-library-<name>/`), and `packs/<name>/library/`; at the level `connected`, the types and the documentation of the library (below); with no pack, level 1 of [canvas-library-setup](../canvas-library-setup/SKILL.md) first | Which component and which token carry each decision? |
| 4 | [Screen files](../../screen-files.md) | How is the screen written in `screens/`? |
| 5 | `canvas-screen-design`, section 7 | Does the task go through the screens, can each person use them, and what must the user know? |
| 6 | `canvas check -- <the screens that you wrote>` | Does the code keep to the library: no plain element, no inline `style`, no raw value, no link to no screen? |

In each step:

1. **The task.** Write down, in one or two lines each: the task in the words of the person, with real values; the situation; the scenario as a list of actions and answers. Take them from the request first, then from the project ("What the project knows" below), and assume only what the two do not say. State each thing that you assumed. Ask the user only when you cannot assume a task.
2. **Decide what the screens need.** Decide the screens of the flow, the fields, the messages and the states before you choose a component.
3. **Choose the parts** with the pack of the library. In `packs/<name>/AGENTS.md`, the section "Requests" is for the edits of the editor: skip it for a new screen. Run `canvas status` when you do not know the level of the library. With no pack (level `none`), do level 1 of the skill `canvas-library-setup` (one command, `canvas init`), then go on. At the level `connected`, see "Before the tokens are set up" below.
4. **Write the files** as [Screen files](../../screen-files.md) says: one file for one screen, `export const meta = { title, width }`, only the library, no state and no handlers, and no component by your own decision (an own component in `components/` only when the user asks for the part, as Screen files says). Each state is a full file with `stateOf`; a screen at a different width is a full file of its own (`<name>-mobile.tsx`). Use real and a little awkward content, never placeholder text. **Link the flow:** a control that leads to a drawn screen gets `href="#/<screen id>"`. A control whose target is not drawn has no link. A screen that was brought as it is takes a link too, when the new screen opens from it: give its control, or the name of its row, the address of the new screen, change nothing else in it, and name the link in your report.
5. **Walk the task** through the screens and check access, as section 7 of `canvas-screen-design` says.
6. **Check:** `canvas check -- <the screens that you wrote>`, then `canvas build` (in a host, the build can fail before any work: `AGENTS.md` says what to do). Fix each finding. With the editor open (`canvas status` prints the address of a dev server that runs), read `.canvas/issues/<screen id>.json` too: it says what only the page shows, such as a content that is wider than the screen (kind `layout`). An item with `"set": "library"` is a default of a component of the library, not a deviation: leave it.

Step 6 is the one check that you can run with no browser: you do not see the screen, and the check reads the code. Fix each finding before you report. Three findings can stay, and you name each one in your report with its reason: one that an explicit instruction of the user asked for; a plain element that the library skill permits for a purpose (the one `svg` of a chart); and a value with no token that the design skills permit and the library has no scale for. Do not make a finding go away by a different spelling of the same value (a number in place of `'13px'`): use the token.

Do not start at step 3. An agent that chooses components first and checks them later keeps the structure that it built: a check finds a weak label, but it does not remove a screen that the task did not need.

**Report** as section 7 of `canvas-screen-design` says, in about ten lines: what you took from the project and from where, what you left out, what the screens assume, the states and the behavior that are not drawn, the controls with no link, and each finding of the check that stays, with its reason.

## What the project knows

The design skills are a base: general rules that hold for each product. They do not know this product. The project does: who uses it, for what work, how often, in which words. When the project is in an application (the folder of `AGENTS.md` is a folder of the application), read this before step 1. You often know a part of it already; do not read a file two times.

- **The instruction files and the documents of the application:** `AGENTS.md`, `CLAUDE.md`, `.github/copilot-instructions.md` and `README.md` at the root of the application, and its `docs` folder. Take from them the people who use the product, their work, the words of the product, and each convention of its screens.
- **A page of the application that is near the new screen:** the page of the same section, or one with the same kind of content. Take from it the words, the kind and the count of the data, how much one screen holds, and what is around the content.
- **The shell:** when the pages of the application sit in a shell (a navigation, a header, a context line), the new screen sits in the same shell: the same sections, in the same places, with the section of the screen marked. Build it from the parts of the library; do not copy a component of the application for it unless the user asks ("Bring a screen that exists" below).

What the project says wins over what you would assume, and a convention of the project wins over a rule of the design skills where the two differ: name each such case in your report, in one line with the convention and the rule. The project gives the context and its conventions; it does not make a rule of the design skills go away by silence. Where the project says nothing, the design skills apply.

Do not copy the look of a page of the application into the screen: the look is the library's. A page is evidence of the task and of the context, not a template.

## Bring a screen that exists

The user asks to bring, copy or import a screen that the application already has (a page of a prototype in the host) onto the canvas. The task is the same screen, not a new one: the sequence above and the design skills do not apply. Do not replace a part, do not change a text, do not remove a deviation. The canvas shows each deviation from the library; that is what the user wants to see.

1. **Read the page** and each component that it renders. List what is not from the library: the components of the application, the plain elements, the values with no token.
2. **Ask the user one time** when the page has components of the application and the user did not say what to do with them. Name the components, and give the two ways: bring them as they are (the canvas marks them as not from the library, and the user can edit them there), or replace them with the nearest parts of the library (the screen then looks different). When you cannot ask, bring them as they are, and say so in your report.
3. **Write the screen file** in `screens/<flow>/`, with `meta` (the flow from the area of the application, the name from the page, the title from its heading): the markup of the page as it is, with the parts of the library imported from the package or by a relative path. A frame does not read an alias of the bundler of the application (`@/components/…`): write such an import as a relative path, in the screen and in each copied component. Copy each component of the application that the screen needs into `components/`, one file for each, with the path of its source in a comment at its top, and import it from there. The copy is what the user edits on the canvas; the application does not change. A stylesheet that a component imports comes with it. When the page takes its look from a stylesheet that the entry of the application loads (a global file of classes), import that file in the screen file, from its place in the application. A frame cannot load what a build step of the application makes (classes that a tool writes at build time): name it in your report, with what the screen then lacks.
4. **One state, with fixed values.** A frame has no running application: put a fixed value in place of each thing that needs one (the data of a server, a router, a store, a function for translations), with the real values of the page where you can read them. Remove the state and the handlers, and keep the markup of the one state that you chose. Write the rows of a list out, one for each item of the data, thus each row is its own element on the canvas. A handler that only goes to a different page is a link: give the control the address of that screen when it is drawn, and no link when it is not. A different state of the page is a state file (`stateOf`), when the user asks for it.
5. **Keep each deviation:** a plain element, a `className`, an inline `style`, a raw value stay as the page has them.
6. **Check:** `canvas check -- <the screen>` and `canvas build`. The findings that the page brought (`not-library`, `inline-style`, `raw-value`, `class-name`) stay: they are the deviations. Fix only what stops the screen from rendering, and a link to no screen.

**Report:** the state that you chose, each thing that you replaced with a fixed value, the components that you copied with their sources, and the count of the findings by kind. The notes of the check count the deviations inside each copied component (the plain elements, the `style` attributes, the raw values); give these counts too. Do not offer to fix the deviations unless the user asks ([canvas-check](../canvas-check/SKILL.md) is that job).

## Before the tokens are set up

At the level `connected` (`canvas status` says so: `tokens.json` has no token, and the pack has often no library skill and no `AGENTS.md` yet), the screens render with the library, and you can make them. Do not wait for level 2, and do not do it unless the user asks: the user's task is the screen.

- **The provider first:** when `packs/<name>/library/provider.tsx` only renders its children and the entry of the host application puts a theme provider, base styles or a stylesheet of the library around the application, do step 1 of level 2 of `canvas-library-setup` (the provider) before the screen. It is a part of the setup, not a change of the library, and it takes minutes; without it the screens show the default look of the library, not the look of the product. Name it in your report.
- **The parts:** read the types of the library in `node_modules/<package>/` (in a host, the `node_modules` of the host root: `../node_modules/<package>/` from the folder of `AGENTS.md`) (the props of each component, its variants, its sizes) and the documentation in the package (`README.md`, a `docs` folder, `llms.txt`, a skill). `sources` in `pack.json` names the packages and folders that count as the library; import only from them.
- **The values:** use the props and the scales of the library (a spacing step, a color role, a text variant), as its types name them, never a raw value. Where you cannot tell the form of a value from the types, choose the prop that the documentation shows, and name it in your report.
- **The check:** `canvas check` finds a plain element, a `style`, a `className` and a raw text value (`'13px'`). With no `scaleKeys` in `pack.json` it does not find a number of pixels (`fontSize: 14`): write none. The editor counts no value as a deviation yet, thus the check is the proof.
- **The report** names that level 2 is open, with the sentence that sets it up: `Set up the tokens of the library as the skill canvas-library-setup says.` After it, the editor links each value, and a value that no token gives becomes a deviation.

## Who decides what

- **An explicit instruction of the user** (in the prompt, or in a comment of a request): it wins over the design skills, over a default of the library, and over the guidance of the library. The user owns the screen and can break a rule. Do what the instruction says, and name each rule that it breaks in your report, in one line with the rule and its source, thus the user can change the decision. Do not refuse, and do not put the nearest permitted form in its place. Only an instruction that states the thing itself counts ("make this button pink", "use a confirmation here"): a general wish ("make it stronger") is done inside the rules. Three things stay fixed, because they are how the tool works and not guidance: the form of a screen file ([Screen files](../../screen-files.md): one file for one screen, `meta`, no state and no handlers, no import from the tool, a component only from the library or from `components/`); no change of the library, of its pack or of `tokens.json` (the provider step of "Before the tokens are set up" is part of the setup); no change outside `screens/` and `components/` for a request. A part that the user asks for and the library does not have is not refused: it is an own component in `components/`. The five items below hold where the user gave no such instruction.
- **What the project says about its product** (its people, their work, its words, a convention of its screens that a document states): it gives the task and the situation, and a stated convention wins over a rule of the design skills ("What the project knows" above). Report each conflict.
- **Behavior and content** (which steps, which fields, an undo and no confirmation, a table and no chart): the design skills decide, and the library carries the decision out. If the library has no part for it, build it from the simplest parts of the library and tell the user.
- **The look** (colors, shapes, text styles, the place of the parts of a component): the library decides. Its default wins over a rule of the look in a skill, and the agent does not override a component.
- **Layout** (where a component is, how wide, what is next to it): the agent decides, with the scales of the library.
- **An explicit rule in the library's own guidance** (a skill or a guide that comes with the design system): it wins over the design skills, also on behavior and content, because it is a decision of the owners of the product. Where that guidance is silent, the design skills apply. The agent reports each conflict to the user, with the two rules. A component that only exists is not such a rule.
