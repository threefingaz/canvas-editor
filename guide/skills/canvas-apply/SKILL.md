# Apply the canvas requests

The user edited screens in the canvas editor. The editor saved each change as an item of a request file, `.canvas/requests/<screen id>.json`. Your task is to write each item into the code of its screen, and to remove the item.

The full guide is [Requests](../../requests.md): the format of an item, one example of each kind, and the rules. Read it before you change a file. This skill is the sequence of the work. A path in this skill is relative to the folder of the project (the folder of `AGENTS.md`); a Markdown link is relative to this file. `canvas <command>` runs as `AGENTS.md` says.

1. **List the request files:** each `.json` file in `.canvas/requests/`, also in its sub folders. With no file, tell the user that there is no request, and stop.
2. **Read [Requests](../../requests.md),** [Screen files](../../screen-files.md), and `packs/<name>/AGENTS.md` with the library skill that it links. At the level `connected` the pack has often neither: use "Before the tokens are set up" in [canvas-screen](../canvas-screen/SKILL.md) (the types and the documentation of the library). With no pack in `packs/`, tell the user that no library is connected, and change nothing. When the only items are `keep` items, "Options" and "After the work" of Requests are enough: a `keep` makes no design decision and needs no design skill.
3. **Run `canvas check` and `canvas build` one time** before you change a screen, thus you know the findings and the errors that were there (in a host, the build can fail before any work: `AGENTS.md` says what to do).
4. **For each request file, one pass:** a `keep` item first; then the edits (`style`, `textStyle`, `text`, `order`, `remove`) from the last line to the first; then the comments on elements from the last line to the first; then the comments on the screen; then the `options` items, last of all, thus each option has each edit and each comment. An option of an element changes only that element, and marks it (not a parent of it) with `{/* canvas-part */}` directly before it, and a `keep` does not write that marker into the base ("Options" in [Requests](../../requests.md)). A comment is a task in the words of the user, and an `options` item is one too: do it with the design skills ([canvas-screen-design](../canvas-screen-design/SKILL.md)) and the library skill, in the sequence of [canvas-screen](../canvas-screen/SKILL.md).
5. **The states follow their screen:** make the same change in each state file of a base screen where the same element is.
6. **Write the request file one time,** at the end of its pass: remove each item that you applied, add a `reply` to each item that you did not apply (`conflict`, `needs-library-change`, `unclear`), keep each item that you did not read, and delete the file when no item is left (and its folder when that is then empty). Read the file again just before you write it.
7. **Run `canvas check -- <the screens that you changed>` and `canvas build`.** Fix what your work added. For each option that you wrote, the notes of the check name the block that its marker gives (`its block is <Stack> at 32:11`), or say that it has no marker: make sure that it is the element that the user chose, or the part that you wrote in its place. A finding that was there before, or that an edit or a comment of the user asked for, stays: name it.
8. **Report** as "After the work" in [Requests](../../requests.md) says: one line for each comment that you did, each new screen file, each rule that a comment broke, and each item with a reply.

Do not change the library, its pack in `packs/`, `tokens.json`, or a file outside `screens/` and `.canvas/requests/`.
